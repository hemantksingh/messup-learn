# Key Management

AWS-managed encryption and decryption service

* Create and control encryption keys used to encrypt your data. Provides centralized control over the lifecycle and permissions of your keys
* Integrates with S3, EBS, RDS and other services to encrypt your data with the encryption keys you manage

## AWS KMS Keys

AWS KMS keys (KMS keys) are the primary resource in AWS KMS. You can use a KMS key to encrypt, decrypt, and re-encrypt data. It can also generate data keys that you can use outside of AWS KMS. Typically, you'll use symmetric KMS keys, but you can create and use asymmetric KMS keys for encryption or signing. AWS KMS key is a logical representation of an encryption key. It contains the key material used to encrypt and decrypt data. The key material for a KMS key can be

* generated by default, within AWS KMS. The key material cannot be extracted, exported or viewed. Also, you cannot delete this key material; you must delete the KMS key. The key material for the KMS key is generated within shared HSMs (Hardware Security Module) managed by AWS KMS.
* imported from your own key management infrastructure into a KMS key
* created in the **AWS CloudHSM** cluster associated with an [AWS KMS custom key store](https://docs.aws.amazon.com/kms/latest/developerguide/custom-key-store-overview.html). When you create an AWS KMS key in a custom key store, AWS KMS generates and stores non-extractable key material for the KMS key in an AWS CloudHSM cluster that you own and manage. When you use a KMS key in a custom key store, the cryptographic operations are performed in the HSMs in the cluster.
* held outside AWS in an **External Key Store (XKS)**, the second custom key store type (2022). The key material stays in an HSM or key manager you run yourself and KMS forwards each cryptographic request to it through an XKS proxy.

A **Hardware Security Module (HSM)** is a physical computing device containing one or more secure crypto-processor chips that safeguards and manages digital keys and performs encryption and decryption functions. The default AWS KMS key store is a shared service protected by HSMs validated at FIPS 140-3 Level 3. If your security requirement mandates a dedicated HSM (CloudHSM is also FIPS 140-3 Level 3) with full control of the underlying hardware, or key material that never enters AWS, you can opt for a custom key store.

KMS encrypts at most 4 KB per call, so services and the SDKs use **envelope encryption**. KMS generates a data key and returns it twice, in plaintext and encrypted under the KMS key. The plaintext copy encrypts the data locally and is discarded; the encrypted copy is stored next to the data. To decrypt, the encrypted data key is sent back to KMS, which returns the plaintext data key. The KMS key itself never leaves the HSM.

* AWS KMS keys can be rotated automatically, provided that those keys were generated within AWS KMS HSMs. Since April 2024 the rotation period is configurable from 90 to 2560 days (default 365) and you can also rotate on demand.
* Automatic key rotation is not supported for imported keys, asymmetric keys or keys generated in an AWS CloudHSM cluster using the AWS KMS custom key store. On-demand rotation of imported key material is supported since June 2025.
* There are 3 ways to control permissions to KMS keys
  * Using the key policy (resource based policy attached to the KMS key) - the full scope of access to the KMS key is defined in a single document (the key policy)
  * Using IAM policies (policies attached to IAM identity) in combination with the key policy - manage all the permissions for your IAM identities in IAM
  * Using grants in combinations with the key policy - enables you to allow access to the KMS key in the key policy as well as allow users to delegate their access to others

## How do I protect my keys?

KMS keys fall into three categories depending on who creates and controls them

* **Customer managed keys** are created and controlled by you. You write the key policy, manage rotation and pay for the key. The key material is generated by KMS by default; importing your own material (BYOK) or using a custom key store are the alternatives

* **AWS managed keys** (`aws/s3`, `aws/rds` and so on) are created by a service in your account on your behalf. You can see them and their use in CloudTrail, but the key policy is read-only and you cannot delete them

* **AWS owned keys** belong to a service and are shared across many accounts. They are not visible in your account and you cannot set a key policy on them. S3 default encryption (SSE-S3) uses AWS owned keys

* Key deletion for a customer managed key is scheduled, not immediate. The mandatory waiting period is 7 to 30 days (default 30), the key cannot be used while deletion is pending and the deletion can be cancelled. It is still destructive, since data encrypted under the key becomes unrecoverable, so disable the KMS key first and check that nothing breaks before scheduling deletion
